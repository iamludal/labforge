# 🤝 Contributing to labforge

Thanks for your interest in labforge! Bug reports, documentation fixes, ideas and pull requests are all welcome.

By participating in this project, you agree to follow its [code of conduct](CODE_OF_CONDUCT.md).

## 💡 Ways to contribute

- **Report a bug** or **suggest a feature** by [opening an issue](https://github.com/iamludal/labforge/issues/new/choose). Search existing issues first.
- **Improve the documentation**: typos, unclear explanations, missing examples.
- **Fix a bug or implement a feature.** For anything larger than a small fix, open an issue first to discuss the approach.
- **Report a vulnerability** privately, as described in the [security policy](SECURITY.md). Do not open a public issue.

## 🧰 Development setup

Requirements: [Bun](https://bun.sh) 1.2 or later.

```bash
git clone https://github.com/iamludal/labforge.git
cd labforge
bun install
bun run example
```

`bun run example` builds labforge and serves the example labs from [examples/labs](examples/labs) at <http://localhost:4000>.

### 📜 Scripts

| Script              | Description                                                                                       |
| ------------------- | ------------------------------------------------------------------------------------------------- |
| `bun run build`     | Builds the CLI (`lib/`), the browser runtime (`assets/app.js`) and the styles (`assets/app.css`). |
| `bun run typecheck` | Type-checks the CLI and the browser runtime.                                                      |
| `bun run example`   | Builds labforge, then serves the example labs with live reload.                                   |

The dev server only watches the labs directory. After changing labforge itself, run `bun run build` again and restart `bun run example`.

### 📁 Project structure

```text
src/
├── cli.ts             # command-line entry point
├── serve.ts           # dev server with live reload
├── paths.ts
├── build/             # Markdown → labs pipeline
│   ├── index.ts       # lab discovery, chapters, links, images, output
│   ├── parse.ts       # frontmatter schemas and validation
│   ├── steps.ts       # splitting a document into steps
│   ├── markdown.ts    # Markdown → sanitized HTML
│   ├── highlight.ts   # Shiki syntax highlighting
│   └── types.ts
├── templates/         # HTML of the lab and catalog pages
├── runtime/           # browser script: navigation, progress, theme
└── styles/            # Tailwind CSS entry point
examples/labs/         # example labs, also used as the live demo
docs/                  # user documentation
```

`lib/` and `assets/` are generated by `bun run build` and are not committed.

## 📏 Guidelines

- **Keep the output self-contained.** Generated sites must not depend on external services, CDNs or trackers.
- **Keep the reader experience accessible**: semantic HTML, keyboard support, visible focus, `prefers-reduced-motion`.
- **Keep security in mind**: Markdown content must stay sanitized, and the build must not read or write outside the input and output directories.
- **Be careful with new dependencies.** Discuss them in an issue first.
- **Do not break existing labs.** Changes to the lab format, step identifiers or saved progress need a migration path.
- **Update the documentation** and, when relevant, the [example labs](examples/labs) along with your change.

## 🔀 Pull requests

1. Fork the repository and create a branch from `main`.
2. Make your change, then check that everything still works:

   ```bash
   bun run typecheck
   bun run build
   bun run example   # review the example labs in your browser
   ```

3. Commit using [Conventional Commits](https://www.conventionalcommits.org): `feat: …`, `fix: …`, `docs: …`, `refactor: …`, `chore: …`. Releases are automated with [release-please](https://github.com/googleapis/release-please), which reads commit messages to pick the next version and write the changelog:
   - `fix:` triggers a patch release, `feat:` a minor release;
   - `!` after the type (`feat!: …`) or a `BREAKING CHANGE:` footer marks a breaking change (a minor release while labforge is below 1.0);
   - other types do not trigger a release.

   When a pull request is squash-merged, its title becomes the commit message, so it must follow the same format.
4. Open a pull request, describe what changed and why, and link the related issue. Add screenshots for visual changes.

## 🤖 AI-assisted contributions

labforge itself is largely written with AI coding assistants. AI-assisted contributions are welcome, as long as you have reviewed, understood and tested the code you submit, and can explain it during the review.
